# 存储模型选型

## 问题

单机 KV 需要把随机写入组织成可恢复、可增长的持久化结构。常见路线如下，MiniKV 实现其中一种。

## 方案对比

| 模型 | 主要用途 | 优势 | 代价 |
|------|----------|------|------|
| **LSM-Tree** | 写密集 KV、时序数据、批量导入 | 写入转换为顺序追加；压缩策略可调；自然连接 WAL、内存表和不可变文件 | 点查可能访问多个文件；Compaction 带来写放大和后台 IO |
| B+Tree（页式） | 读密集数据库、范围扫描、页缓存命中率高的负载 | 路径稳定；范围扫描连续；单个 key 更新后通常无需重写大量相邻 key | 节点分裂、页锁和崩溃恢复复杂；随机写较多 |
| 持久化哈希 | 精确点查、无序对象存储 | 平均点查路径短；无需维护全局顺序 | 不支持有序遍历；扩容和冲突处理复杂；范围查询需要额外索引 |
| Bε-Tree / Fractal Tree | 同时需要范围查询和写缓冲的场景 | 在树节点中批量缓冲更新，兼顾部分树结构与顺序写特征 | 实现复杂，缓冲下推和恢复逻辑较重 |
| 纯追加日志 | 小型日志型 KV、原型和审计记录 | 写路径短；每次更新只追加 | 点查依赖内存索引；垃圾回收成本随日志增长；启动回放时间长 |

## MiniKV 的选择

**采用 LSM-Tree。**

1. 写入以顺序追加为主，与 WAL、MemTable、SSTable、Flush、Compaction 同构。  
2. 与 RocksDB 一类引擎分层一致，便于对照工业实现。  
3. 分布式阶段只需把已提交命令 Apply 进引擎，不必更换存储模型。

这一选择放弃了 B+Tree 较稳定的读放大、原生范围页扫描和原地更新，也放弃了持久化哈希的短点查路径。MiniKV 的教学主线集中在 WAL、MemTable、SSTable 和 Compaction 的相互约束，并不同时维护第二套磁盘布局。

LSM 的三种放大构成核心权衡：

| 指标 | 来源 | MiniKV 中的表现 |
|------|------|-----------------|
| 写放大 | Compaction 重写已经落盘的数据 | Size-Tiered 延迟合并，以较高读放大换取较低合并频率 |
| 读放大 | 一个 key 可能存在于多个 SST | MemTable 优先；SST 中按 sequence 比较所有候选版本 |
| 空间放大 | 旧版本和墓碑在合并前仍占空间 | Compaction 删除被更新覆盖的旧版本；墓碑保留到能够安全判定无旧值的阶段 |

## 与代码的对应

```text
Put → WAL 追加 → MemTable
MemTable 满 → Immutable → 后台 Flush → SSTable
多 SST → Size-Tiered Compaction
重启 → 装载 MANIFEST / SST，并回放未刷完的 WAL
```
