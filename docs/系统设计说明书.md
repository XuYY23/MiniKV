# MiniKV 系统设计说明书

MiniKV 是一套用 C++ 实现的键值（KV）存储系统，覆盖**单机存储引擎**与**分布式 KV 服务**两层能力。系统面向需要理解现代存储与分布式基础组件的开发者与学习者：可运行、可测试、可对照主流实现阅读设计说明。

| 项 | 内容 |
|----|------|
| 系统名称 | MiniKV |
| 实现语言 | C++17 |
| 运行平台 | Linux |

---

## 1. 系统概览

### 1.1 系统提供什么

MiniKV 分为两个连贯层次：

**单机引擎**负责把数据可靠地留在一台机器上：写入先记日志，再进入内存表，再刷成磁盘上的有序文件，并在后台合并整理。对外提供嵌入式 API 与命令行工具，支持 `Put` / `Get` / `Delete`，进程崩溃后可按设计恢复已成功返回的写入。

**分布式服务**在引擎之上增加多副本共识与分片：客户端通过 TCP RPC 访问服务；请求按 key 落到对应分片；每个分片由一组 Raft 副本复制日志，提交后再应用到本机引擎。`MemoryTransport` 用于确定性测试，`TcpRaftTransport` 承载跨进程节点通信。

### 1.2 在技术谱系中的位置

下表给出 MiniKV 与常见系统的概念对应关系：

| 常见系统 | 对应到 MiniKV |
|----------|----------------|
| RocksDB | 单机引擎一侧：LSM、WAL、MemTable、SSTable、Flush、Compaction |
| etcd、TiKV | 分布式一侧：Raft 复制、RPC、分片与客户端访问 |

MiniKV 体量更小、路径更收敛，适合在一个仓库里把上述分层从引擎走到分布式；并不提供与上述系统的接口兼容。

### 1.3 系统明确不支持的能力

MiniKV 聚焦 KV 存储与复制主路径，下列能力不在系统功能之内：

- SQL 与关系模型  
- 完整事务 / MVCC  
- 自动扩缩容、在线迁片与数据再均衡  
- 跨分片分布式事务  
- 多机房、安全认证与生产运维套件  
- 与 RocksDB、etcd、TiKV 的接口或行为兼容

## 2. 总体架构

下图是 **MiniKV 分布式形态下的内部层次**，也是一次写入的调用顺序。只使用单机能力时，主要落到最下层的本地存储引擎（单机LSM引擎）。

```text
客户端 (Client / CLI)
        │  KV RPC（Put / Get / Delete）
        ▼
┌───────────────────┐
│  路由层            │  根据 key 计算分片
│  hash(key) → shard │  定位该分片当前 Leader
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐
│  Raft Group        │  每个分片一组：Leader + Follower
│  · 追加日志         │  多数派确认后提交
│  · 持久化 term/log  │
└─────────┬─────────┘
          │ Apply（已提交日志）
          ▼
┌───────────────────┐
│  KV 状态机         │  把日志里的命令变成引擎调用
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐
│  单机 LSM 引擎     │  每节点本地数据目录
│  WAL               │
│  MemTable          │
│  SSTable           │
│  Flush / Compaction│
└───────────────────┘
```

节点之间另有一套 **Raft RPC**（投票、追加日志/心跳），与客户端 KV RPC 分离：前者维持副本一致，后者承载业务读写。

**读路径（默认）：** 客户端将 Get 发到对应分片的 Leader，Leader 在本地引擎查询后返回，读到的是该分片已提交视图。

**进程与数据布局：** `minikv_node` 让每个副本运行在独立进程并使用独立数据目录（引擎文件 + Raft 持久化状态）。分片数量与副本成员由静态配置给出，不做运行时自动搬迁。`minikv_server` 是单进程多分片教学入口，两种形态复用相同的 RaftNode、状态机和 RPC 协议。

## 3. 单机引擎设计

### 3.1 目标

在单进程内提供可嵌入的本地 KV：数据落盘、崩溃可恢复，并具备内存表刷盘与文件合并能力。该层完成后即可单独使用；分布式阶段将其作为 Raft 状态机的后端。

### 3.2 存储模型：采用 LSM-Tree

常见持久化 KV 组织方式对比如下：

| 模型 | 在做什么 | 优势 | 不足 |
|------|----------|------|------|
| **LSM-Tree** | 先写日志与内存，再顺序刷盘，多层文件合并 | 写路径以追加为主；WAL、MemTable 与 SSTable 构成连续持久化流程 | 读可能访问多个文件；需要 Compaction |
| B+Tree（页式） | 在磁盘页上维护有序树，常原地更新 | 点查与范围读较稳 | 随机写与页管理重；与「先刷盘再合并」的组织方式差异大 |
| 哈希持久化 | 按哈希槽位组织 | 点查可以很快 | 范围弱，扩展与部分恢复更碎 |
| 纯追加日志 | 几乎只追加，启动时重建 | 模型最简单 | 回收与大规模恢复代价高 |

**本系统采用 LSM-Tree。**  
写入以顺序追加为主，延迟随机落盘的代价；WAL、MemTable、SSTable、Flush、Compaction 在同一套模型里闭环，也与 RocksDB 一类引擎的分层一致。系统只落地这一套存储组织，不并行维护第二套引擎。

### 3.3 内存索引：采用 SkipList

MemTable 需要一种内存结构承载最新写入，并在刷盘时按序导出。

| 结构 | 优势 | 不足 |
|------|------|------|
| **SkipList** | 有序、实现清晰，LSM MemTable 的常见选择 | 层高与常数开销需要权衡 |
| 红黑树等有序树 | 有序，结构经典 | 与常见 LSM MemTable 实践不如SkipList贴合 |
| 哈希表 | 点查快 | 无序，刷盘前往往还要排序 |

**本系统采用 SkipList 作为 MemTable 索引。**  
与 LSM 常见做法一致，有序遍历可直接服务于 Flush 写出 SSTable。

### 3.4 写入、读取与恢复

```text
Put:
  追加 WAL → 写入活跃 MemTable
  若 MemTable 达到阈值：
      当前表变为 Immutable（只读）
      新建一张活跃 MemTable 继续接写
      后台 Flush 把 Immutable 写成 SSTable
  后台按策略 Compaction 合并 SSTable

Get:
  先查活跃 MemTable，再查 Immutable（若有）
  再查询所有可能包含该 key 的 SSTable
  比较候选 internal key 的 sequence，最大者生效（含删除标记）

恢复:
  加载 MANIFEST 与 SSTable
  回放 current WAL；Flush 未完成时同时回放 previous WAL
  重建 MemTable
```

### 3.5 WAL

- 作用：MemTable 尚在内存时，用顺序日志保住已成功返回的写入。  
- 次序：先写 WAL，再改 MemTable。  
- 恢复：启动时回放 MANIFEST 引用的 WAL。测试使用 `_exit` 模拟未执行析构和 `Close` 的进程崩溃。

### 3.6 MemTable、Flush 与写入不阻塞

| 环节 | 做法 |
|------|------|
| 活跃表 | 只接受当前写入 |
| 写满 | 整表转为 Immutable，立刻换新的活跃表 |
| Flush | 后台线程把 Immutable 序列化为新的 SSTable，并更新文件清单 |
| 为何写不堵在刷盘上 | 前台只写新活跃表；刷盘打在 Immutable 上，二者并发 |
| 背压 | 前一张 Immutable 尚未刷完时等待后台 Flush，防止内存无限涨 |

MemTable 冻结时同时轮换 WAL。MANIFEST 在 Flush 期间保留 `previous WAL + current WAL`：前者保护 Immutable，后者保护新的活跃表。新 SST 同步完成并写入 MANIFEST 后，previous WAL 才能删除。Compaction 同样先安装包含输出 SST 的新 MANIFEST，再删除输入文件。这一顺序保证每个崩溃点至少保留一条完整恢复路径。

Flush 产出的 SSTable 不可变：有序数据区 + 文件内索引/元数据。删除操作写入墓碑；Compaction 清除被墓碑覆盖的旧值。当前实现保留最终墓碑，因为不存在能够证明所有更旧层均已覆盖的分层边界。

### 3.7 Compaction：对比两种策略，实现 Size-Tiered

| 策略 | 做法概要 | 优势 | 不足 |
|------|----------|------|------|
| **Size-Tiered** | 按文件大小分代，同类合并成更大文件 | 规则直观，实现路径清晰 | 读放大可能更大 |
| Leveled | 分层级，控制层内重叠与容量 | 读更稳 | 实现与调参更重，写放大更明显 |

**本系统实现 Size-Tiered Compaction。**  
在「写放大 / 读放大 / 实现复杂度」之间更均衡，足够支撑完整的合并回收路径。Leveled 的机制与适用场景在对比中说明，本系统不并行实现第二套合并策略。

### 3.8 单机对外接口

```text
Open / Close
Put(key, value)
Get(key) → value
Delete(key)
```

提供嵌入式 C++ API、单机 CLI，以及引擎级测试与 Benchmark。

## 4. 分布式服务设计

### 4.1 目标

在多节点上提供统一的 KV 访问：分片路由、Raft 复制、RPC、客户端库。每个节点本地仍运行第 3 章的引擎；**共识解决的是「多副本同意同一段操作日志」**，存储细节仍由引擎负责。

### 4.2 Raft

本系统实现 Raft 协议，使三节点（或同分片多副本）可以选主、复制日志、在法定多数派持久化后提交，并把命令应用到状态机。成员变更采用 joint consensus：联合配置阶段同时满足旧集合和新集合的多数派，然后提交最终配置。新成员的网络地址需预先出现在传输层地址表中。

| 能力 | 说明 |
|------|------|
| 角色 | Follower / Candidate / Leader |
| 选举 | 选举超时、RequestVote、任期 term |
| 复制 | AppendEntries 复制日志与心跳 |
| 提交 | 多数派持久化后推进 commit，再 Apply |
| 持久化 | `currentTerm`、`votedFor`、日志条目落盘，进程重启可恢复 |
| 写确认 | `Propose` 只在目标日志已经提交后返回成功；少数派 Leader 不能确认写入 |
| 读取 | Leader 在读取前通过多数派通信确认领导权 |
| 状态机 | `StateMachine::Apply` 返回状态；成功并持久化后才推进 `lastApplied` |
| 读屏障 | 新 Leader 首次读提交当前任期 no-op，旧任期已提交前缀先完成 Apply |
| 快照 | `CreateSnapshot` 截断已 Apply 日志；落后副本通过 `InstallSnapshot` 追赶 |
| 成员变更 | joint consensus 对旧、新成员集合分别计算多数派 |
| 故障 | 杀掉 Leader 后可重新选主并继续写入（提供演示步骤） |

状态机与 Raft 解耦：

```text
Raft 只负责：日志达成一致并提交
StateMachine 负责：把提交的命令变成对单机 LSM 引擎的调用
```

持久化层实现 `RaftStorageInterface`，文件实现为 `RaftStorage`。它保存 hard state、带基准索引的日志后缀和快照，文件均有 CRC-32C 校验并通过临时文件、fsync、rename、目录 fsync 原子安装。状态机实现 `StateMachine` 的 Apply/CreateSnapshot/RestoreSnapshot 接口，并遵守幂等 Apply 契约；最后一条 Apply 在崩溃边界上可能重放。

### 4.3 RPC

| 通道 | 用途 |
|------|------|
| Raft RPC | `TcpRaftTransport` 发送投票、追加日志与心跳 |
| 快照 RPC | `InstallSnapshot` 向日志落后于压缩边界的副本安装状态快照 |
| KV RPC | `KvRpcService` 与 `RemoteClusterClient` 承载 Put / Get / Delete |

协议采用长度前缀 TCP 帧，包含 magic、版本、消息类型和 request id。服务端管理连接线程的完整生命周期；客户端设置收发超时，并校验响应类型与 request id。

### 4.4 数据分片

| 项 | 选择 |
|----|------|
| 规则 | 静态分片，例如 `hash(key) % N` |
| 与 Raft | **每个分片一个独立 Raft group** |
| 路由 | 客户端（或轻量代理）计算分片并查找 Leader |
| 不做 | 自动迁片、再均衡、弹性扩缩 |

多分片时，不同 Raft group 可并行处理不同 key 上的写入。

### 4.5 客户端

- 数据操作：`Put` / `Get` / `Delete`  
- 进程内接口：`ClusterClient`  
- 网络接口：`RemoteClusterClient`  
- 命令行入口：`minikv_cluster_cli`、`minikv_server`、`minikv_remote_cli`

## 7. 实现路径

系统由两条实现路径组成，分布式状态机复用单机引擎：

1. 单机引擎：WAL → MemTable（SkipList）→ 非阻塞 Flush → SSTable → Size-Tiered Compaction → CLI / 测试 / 单机 Benchmark  
2. 分布式服务：RPC → 单分片 Raft（持久化 + 状态机接引擎）→ 静态多分片 → 客户端与故障演示 → 分布式 Benchmark

---

## 8. 能力范围（摘要）

**单机：** WAL 支持真实进程崩溃恢复；写满 MemTable 后后台刷盘且前台继续写；Size-Tiered Compaction 合并 SST；API、CLI 与单机 Benchmark 组成完整入口。  

**分布式：** Raft 完成选主、持久化复制、提交、Apply、快照追赶与 joint consensus 成员变更；TCP 承载 Raft 和 KV RPC；静态分片与客户端完成集群读写删；故障测试覆盖少数派拒绝、Leader 切换和副本追赶。
